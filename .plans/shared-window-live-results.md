# Shared-window probe: live evidence, November 1, 2026

Status: live feasibility session completed and owned resources stopped, November 1, 2026, approximately 20:40 UTC. Three user-controlled lock/unlock cycles were exercised on one Mac and one physical Vision Pro. This is not a reliability sign-off. The isolated implementation is [shared-window-probe](../experiments/shared-window-probe/README.md); production sources are unchanged. The user authorized machine takeover and explicitly requested **no automatic session cutoff**. The host uses manual stop; individual provider calls still have deadlines. Lock/unlock remains user-controlled.

## What the live session has established

Three Mac windows (native fixture, Chrome fixture, and the disposable iPhone Simulator window) can be shared independently to physical Vision Pro. The user described these streams as looking good. The native path is ScreenCaptureKit → hardware-required VideoToolbox H.264 → pinned TLS → native visionOS video rendering. Capture is configured for up to 30 fps and 1920×1440, with an 8 Mbps average bitrate target per encoder. These are settings, not measured headset delivery rates; the bitrate target is not a hard bandwidth ceiling.

There is also a working independent simulator path: WDA screenshots and interaction through Appium. After fixing a transport bug, the user confirmed the continuous JPEG viewer was stable while unlocked. The host relay measured about **14 fps** with 15 fps requested. At 60% source scale (702×1520) and JPEG quality 25, observed bandwidth was roughly **15–20 Mbps**, varying with content. An earlier 75% scale / quality 40 sample was about 27 Mbps. Those rates are host measurements, not headset-presented fps or glass-to-glass latency.

The original PNG polling path is too slow for interactive use. `simctl` capture took about two seconds, followed by a one-second polling delay: roughly one update every three seconds in this run. A “1 fps” label described a ceiling and was misleading. Keep this path for observations/diagnostics, not the primary fallback experience.

The fixture's retained scroll position also caused a cold-interaction lookup to fail: Settings was outside the current AX tree. Observing the tree and scrolling back allowed typing. This supports the user's preference for an adaptive orchestrator; a fixed “find Settings immediately” script is brittle even when the provider works.

Keep **session lock**, **display availability**, **system sleep**, and **provider health** as separate facts in the eventual capability snapshot. A single desktop-state enum loses useful information when a locked display sleeps. Also distinguish a source that is producing frames from a viewer that has actually received/presented them. Desktop capture/input should remain unavailable, while device providers can be probed independently. Lock detection currently uses isolated undocumented CGSession/IORegistry signals plus public session/sleep notifications; three observed lock/unlock cycles do not establish cross-version reliability.

## Bugs discovered through real headset use

1. **Lease expiry looked like stream failure.** On this machine the CGSession locked key is absent while unlocked. The initial 30-second diagnostic unlocked lease expired, correctly pausing capture but producing a poor experience. Added IORegistry `IOConsoleLocked` evidence; true from either lock source wins, with session/sleep guards. Unknown still blocks desktop control.
2. **Obsolete target connections leaked.** Unknown stream targets were accepted but never produced data, and the server did not continue reading to notice client close. Restored viewer windows exhausted the 12-peer cap. Unknown targets now return 404; stream connections observe EOF; viewer panels for removed targets dismiss. Twenty rejected stale-target requests followed by successful valid streams verified the fix locally.
3. **`simctl screenshot -` did not deliver PNG bytes on stdout here.** It wrote a file named `-`. Use a private temporary file with explicit cleanup and size limits.
4. **Foundation demultiplexes WDA multipart JPEG.** URLSession delivers per-image response callbacks and strips MIME headers. The adapter must accept those responses and reconstruct its bounded parser input. Local complete JPEG relay was verified.
5. **Busy JPEG send caused flashing.** The server disconnected on any non-H.264 packet arriving during an outstanding send. At continuous JPEG rates this caused repeated black/image/reconnect cycles on Vision Pro. It now drops independent frames and redundant status packets while one send is outstanding, retaining a two-second stall limit. Pauses still invalidate stale imagery. All four streams stayed connected in the short follow-up, and the user reported “Stable now.” This is not a congestion/long-soak certification.
6. **A successful test build was not proof tests existed.** XcodeGen target-scheme configuration used the wrong nesting. Build checks now inspect the `.xctestrun` for the actual test target rather than just checking that a file exists.

## Implications for the product

Use native window streaming for unlocked desktop apps. Keep simulator-device streaming and device automation as a separate provider that the orchestrator can choose when the desktop becomes unavailable. Terminal MCP and the global agent should call these same target-bound operations; they should not each own capture services or permission grants.

Continuous WDA JPEG is useful proof that the locked-desktop fallback can have an interactive frame rate. It is not yet the production bandwidth answer. Evaluate decoding once on the Mac and feeding a hardware H.264 encoder into the same receiver/transport, measuring added CPU, power, text readability and latency. This transcode has **not** been built or measured. A direct device-frame provider may be another future option; do not promise an unsupported private simulator API as the shipping solution.

Retain bounded queues and drop policies even with a better codec. Transport loss/congestion adaptation, receiver-delivery telemetry, pairing, helper ownership/cleanup, and long-run stability still need work. A mature media transport may reduce maintenance compared with growing this experimental HTTP framing into a production streaming stack.

## Continuation and remaining limits

The corrected XCTest artifacts are in `ui-test-2314d154-5282-435f-88f9-2c049811fe61/`; attachments and video are in `xctest-attachments/`. Both assertions failed, and lock sampling crossed unlock. Do not present this as a passing suite or attribute all failures to lock. The switch failure was reproduced unlocked; fresh AX-derived coordinates at the inner control succeeded. The initial helper script also briefly failed on a duplicate log timestamp keyword and an ambiguous old/real test manifest; these orchestration errors were corrected before the actual XCTest run.

The final observed cycle deliberately keeps WDA alive: no cold restart or XCTest interruption. It changes the counter while locked, records device frames, then resumes the same native targets after unlock. This isolates the user-visible stream/recovery question from provider restart testing.

Still unproven: long soak; system sleep/lid closure/logout; booting a new simulator while locked; physical iPhone; headset-delivered fps and end-to-end latency; poor-network behavior; power cost; permission revocation/regrant; broad input contention; standalone XCTest suite reliability; production identity binding and cleanup. These are separate follow-ups, not reasons to turn this disposable spike into another permanent control framework.

### Final observed cycle

The third real lock/unlock cycle completed without restarting WDA. All four input operations had `IOConsoleLocked == true` and desktop state `locked`. Fresh AX snapshots showed **Count 1 → 2 → 3 → 4**; `final-cycle-locked.png` visibly shows Count 4. The device source produced 354 additional frames between snapshots, entirely within locked generation 8. The agent watcher observed unlocked generation 9 and resumed only the same three selected native targets; all returned to `complete` with increasing frame counts. **The user confirmed “Both worked”: continuous JPEG showed the counter changes while locked, and all three native views returned after unlock.** Evidence: `final-cycle.log`, `final-cycle-source-0.xml` through `-3.xml`, `final-cycle-streams.json`, and `final-cycle-locked.png`.

A two-second unlocked source sample showed about 29 fps per native encoder and 14.5 fps from WDA. A single mixed-load host sample was 15.6% CPU / 156,976 KiB RSS with four streams; it excludes Appium/WDA/simulator processes and is **not** a system power or performance benchmark. Server drop counters demonstrate that some frames were skipped. Do not equate these source rates with receiver-presented fps.

### Cleanup and decision

The owned WDA session was deleted, its runner terminated, and only the disposable simulator was shut down. The Mac host was disarmed and terminated, the ProbeViewer process on Vision Pro was terminated, and only the Chrome fixture window was closed. Appium/WDA ports 4727/8117/9117 were clear; the three pre-existing simulators were still booted. Apps, the shut-down disposable simulator and private evidence remain available for a later run; no TCC grants or power settings were reset.

**Decision:** the native-window path and independent simulator fallback are feasible enough to inform the orchestrator design. The user confirmed the final end-to-end locked-view/recovery cycle. This does not justify shipping the spike unchanged. The next engineering work is media efficiency/receiver telemetry, separate lock/display/provider state, automatic recovery within the selected target authorization, production provider identity/lifecycle, and repairing the standalone XCTest suite. Broader resilience and power testing belong to a separate session.


## Remaining feasibility discovery, prioritized

Assessment after the live session: enough evidence to start a thin production integration; the complete workspace-orchestration experience remains unproven. Keep the next discovery tied to decisions that could change the design. Do not expand the disposable probe into a general framework or repeat the same four-fixture demonstration.

| Priority / question | Smallest decisive experiment | Design consequence if it fails |
| --- | --- | --- |
| 1. Can all controllers operate the exact app the user sees? | One real Poncho2 workspace: managed browser plus iOS; global coordinator navigates, user takes over with an unfinished draft, terminal agent inspects/acts through scoped MCP. Repeat with a second workspace carrying similar window titles and a different build marker. Verify same browser/profile/tab, simulator UDID/build, environment, draft, target retention across voice corrections, and immediate Stop. | Adjust target identity, browser execution location, or input arbitration. URL equality is insufficient. Native focus-dependent input may require host-wide serialization. This is the largest untested piece of the overall agent UX. |
| 2. Can iOS be started from scratch while already locked? | Start with a shut-down disposable simulator and no WDA, lock the Mac, then boot, install/launch a development app, start WDA, navigate and stream. Separately test actual system sleep/lid closure only in a new authorized slot. | If locked cold start fails, require preparation before leaving the Mac or disclose the unlock prerequisite. A warm simulator plus a restarted WDA is not proof of this workflow. Keep awake-host requirements explicit; display sleep is not system sleep. |
| 3. Can the requested spatial UX be expressed with supported APIs? | In the actual Vision client, open two terminal/preview pairs with several same-kind windows already present. Resolve the intended instance as the placement anchor, exercise wrist invocation/selection, and observe reopen/restoration and user movement. | Initial relative placement may be sufficient. If reliable clustering/linked movement is essential and unsupported for separate windows, choose an explicit combined workspace presentation or app-owned immersive layout. Do not promise arbitrary repositioning of existing system windows. |
| 4. Is the fallback responsive and efficient enough? | Measure receiver-presented fps, action-to-visible latency, text clarity and total system cost for multiple real surfaces. Compare current JPEG against a native hardware-compressed path; exercise a constrained connection and reconnect. Define acceptable UX thresholds with the user before claiming a performance pass. | Select the codec/transport/provider from measurements. Current ~14 fps source / 15–20 Mbps JPEG establishes feasibility, not production efficiency. Mac-side JPEG→H.264 is an untested candidate, with additional decode/encode cost. |

**Parallel device ownership needs a real check.** Appium supports parallel sessions, but documents distinct simulator identifiers, WDA ports, MJPEG ports and derived-data paths. The experiment used one fixed device/port pair. Test two devices without collision, and test the terminal agent and coordinator sharing one device through a single provider instead of starting competing runners. [Appium parallel-session guidance](https://appium.github.io/appium-xcuitest-driver/latest/guides/parallel-tests/).

**Attention and window layout have platform boundaries.** Ordinary interaction context (explicit selection, invocation window, recent interaction and supported focus) should ground “this window.” Passive knowledge of precisely what the user is looking at is not established by this demo. Apple's privacy model provides eye-driven interaction effects without requiring raw eye data to reach the app. Initial relative placement is documented, while unrestricted movement of existing windows should not be assumed. [Apple privacy guidance](https://developer.apple.com/documentation/visionos/adopting-best-practices-for-privacy), [Apple window placement](https://developer.apple.com/documentation/visionos/positioning-and-sizing-windows).

**Sleep is a separate availability policy.** Apple exposes distinct display-off, automatic-sleep and wake-for-network settings; wake-for-network can be brief and is not a promise that our automation/media workload will remain available. No settings were changed during discovery. [Apple sleep/wake guidance](https://support.apple.com/guide/mac-help/set-sleep-and-wake-settings-mchle41a6ccd/mac).

### Production risks to retain without blocking the first integration

- Stable companion/helper signing and permission attribution across install/update/regrant; the already-authorized standalone probe does not settle onboarding. Undocumented lock signals require conservative handling and OS-version checks.
- Provider identity, per-workspace scope and human takeover shared by UI/global agent/terminal MCP. Scope a terminal agent to granted surfaces; do not hand every terminal an unrestricted global controller. Observe the same target generation and geometry that receive input.
- Lifecycle recovery across provider, host, headset and network interruption. Reconcile existing resources after an ephemeral coordinator restarts; do not replay uncertain typing/submission or create duplicate worktrees. Resource ownership can remain in existing app services without a durable agent framework.
- Voice/model interpretation, cancellation and slash-command routing. Codex orchestrating the spike is evidence that the tools are usable, not a test of the intended embedded voice/coordinator loop. Validate a small set of user-approved conversations through the same operations, rather than building a workflow catalog.
- The failed standalone XCTest assertions remain unresolved. The toggle was also reproducible unlocked and fresh inner-control geometry worked, so these failures do not establish an OS-level locked-control blocker. They do show that reliable computer use needs observation and verified outcomes. Scroll/rotation needs a separate correction and rerun.
- Long soak, memory/battery/thermal cost, network degradation and version coverage remain release checks. Physical iPhone, arbitrary third-party Mac apps, and remote Internet use are separate scope; the simulator/LAN result does not establish them.

**Recommended next move:** implement one small real-app integration using the existing workspace/window services, one shared provider layer, one global coordinator adapter and one terminal MCP adapter. Preserve the user's approved launch examples as test conversations; the larger sample-prompt list still awaits approval. Run the locked-cold-start and exact-instance placement spikes before promising those particular behaviors. No additional machine takeover was performed for this assessment.


**Latest scope refinement:** focus first on the [execution and presentation architecture](orchestrator-execution-path.md): Pi/voice → Mac tool executor → exact app target → Vision gateway and stream receiver → observed result. The [one-preview shared-control cases](shared-control-ux-spike.md) remain subsequent UX tests. The broader risks above remain open; they are not all prerequisites for designing and integrating this path.
