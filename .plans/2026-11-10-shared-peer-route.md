# One Mac connection policy, LAN or direct peer route

November 10, 2026. The user wants the direct route considered for **all SlopZooka Mac↔Vision traffic**, particularly airplanes/hotels where a common usable LAN is undesirable or unavailable. This is a deferred networking improvement, not a prerequisite for the [preview-first rollout](2026-11-10-preview-first-rollout.md). Preserve an inexpensive path to it while implementing previews.

**Assessment:** the existing ownership boundaries are suitable; the concrete networking implementation is still URL/LAN-oriented. We need a small route/transport seam beneath those owners, not another workspace/session service or a second global connection manager. All application traffic can conceptually share a selected network route while retaining independent connections, protocols, backpressure and security boundaries. “One channel” should mean one connection policy to the paired Mac, not one unbounded TCP queue for commands, terminal output and video.

The trusted-origin rules are deliberate: a newly discovered address claiming an existing `hostId` does not earn the host's bearer token. A peer route must authenticate the paired Mac and establish a trusted route binding before credentials are reused. Keep existing pairing identity rather than introducing separate “LAN Mac” and “direct Mac” identities. The probe's bundled pin/token demonstrated test connectivity, not production enrollment or trust migration.

## Smallest useful direction

1. **Retain `CompanionClient` as the connection owner.** Internally distinguish the paired Mac, an authenticated route/route revision, and connections opened for a purpose. Native control requests, terminal content/socket adapters and media subscriptions consume that route. Exact Swift types are an implementation choice; do not build a generic transport/plugin framework before a second adapter needs it.
2. **Add a peer-aware native ingress on the Mac when integrating peer transport.** A narrow `NWListener` adapter can forward the existing application's traffic to its local Node handlers rather than duplicating API/business logic in Swift. The same native networking component can supply LAN and peer candidates; it must not compete with another independent advertisement/route registry. Capture buffers stay on the native media path rather than being relayed through Node JSON.
3. **Keep terminal/control and media independently bounded.** They can use the same selected peer link without being multiplexed into one TCP socket. Preserve terminal delivery/replay semantics and media's freshness/drop policy. Independent sockets still share radio capacity, so measure interactive latency during video load. QUIC/multiplexing is not required to introduce the route seam.
4. **Resolve the WebKit integration before claiming “all traffic.”** First try a real terminal page plus its existing WebSocket, and one representative web preview, through the native peer ingress. The raw probe does not establish that `URLSession` and `WKWebView` can discover/select/use that path with the required origin/trust behavior. If direct URL loading suffices, retain it. If it cannot carry the selected route reliably, evaluate one app-owned local forwarding adapter/native socket bridge. Do not prebuild that proxy, rewrite HTTP, replace xterm, or assert that an injected `URLRequest` exchange controls WebKit. Keep untrusted preview origins/credentials isolated from companion management even when they share a route.
5. **Reconnect within existing owners.** A route change invalidates old resolutions/replies; terminal processes survive and clients reattach using existing protocol behavior. Streams resubscribe to the same authorized source and get fresh codec state. Replay-safe commands retain their IDs; an uncertain non-idempotent action is not automatically resubmitted. A changed TCP path is a reconnect, not a promised seamless socket migration.

When adding the new preview type now, the practical constraint is simply: **resolve media access through the paired-host connection boundary and a stable source reference**. Avoid an independent media-only host discovery/pairing/persistence system. This keeps the future peer upgrade contained without delaying useful previews.

## Travel use and remaining narrow check

Apple documents peer-to-peer Wi-Fi as communication between nearby devices without configuring a shared Wi-Fi network. That makes the airplane/hotel goal plausible without a local router or captive-portal LAN. The Wi-Fi radios must remain enabled. Local connectivity and Internet connectivity are separate: hosted models, remote Git services and web dependencies still need an Internet path from whichever device executes those requests. Carrying SlopZooka traffic over the Mac link does not automatically route every headset app or every external WebView resource through the Mac. [Apple networking guidance](https://developer.apple.com/documentation/technotes/tn3151-choosing-the-right-networking-api).

The [physical experiment](2026-11-10-peer-link-live-results.md) proved authenticated data/reconnect over the Mac's peer interface while infrastructure associations remained intact. It did not establish first-time discovery/pairing or wake/reconnect with neither device associated to an AP. Before promising travel mode, run **one complete product slice** in that condition: find/pair the Mac, open an existing terminal, type and recover after reconnect, fetch a control response, and show one preview. Restore LAN without duplicate Macs, new terminals, repeated commands or unsolicited re-pairing. Include a web preview/HMR or explicitly scope travel support to Mac-rendered streamed previews until that adapter is qualified.

This future test should answer both the no-AP promise and the WebKit/HTTP integration question. It does not justify a generic VPN, system network reconfiguration, whole-device Internet sharing, a new session protocol or a broad pre-implementation architecture project. Do not hardcode `en0`/`awdl0`; the listener exclusion was a diagnostic, not the shipping selection algorithm. Eligibility alone chose LAN in our measured runs. Decide automatic/direct-preferred/fallback policy inside native networking after this actual-client check.

## Discovery lifetime and measurement caveat

Apple specifically recommends stopping a peer-enabled Bonjour browse once a service is selected, before connecting; ongoing browsing can affect performance. The disposable probe kept its browser running for each approximately 17-second trial. Its recorded measurements remain valid for that tested configuration, but they are not an optimized peer implementation or a clean estimate of radio cost. Production should use bounded/on-demand peer discovery, stop it after selection, and rediscover on a meaningful reconnect/menu action—not keep peer scanning alive because a model or a window exists. Current normal-LAN discovery is not proof that perpetual peer browsing has the same cost. [Apple TN3213](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework).

**Decision now:** preserve the shared-host/route seam during preview work; defer the native peer ingress and actual-terminal/web interoperability test. Keep one product connection model and LAN fallback. No new networking implementation or device test is claimed by this note.
