# Agent orchestration and shared surfaces: reading guide

Research and live discovery from October 31–November 1, 2026, with a streaming-strategy reference review on November 6, offline Mac codec benchmarks and Codex harness inspection on November 8, and browser-host/OSS provider investigation on November 9. These documents distinguish proposed architecture, source inspection, local measurements and observed device behavior. They do not implement the production orchestrator or approve the entire sample-prompt catalog.

## Current direction

**Latest qualification:** [Opus 5.5 also works through the same Pi/native adapter](2026-11-09-claude-cua-compatibility.md). The [item #1 contract review](2026-11-09-runtime-integration-contract.md) separates native execution, browser session provisioning, helper lifetime, update compatibility and shipping terms. Two native clients survive independent connection cleanup; a real ScreenCaptureKit startup failure also remains recorded alongside a successful fresh-connection retry. Background Chrome still rejects the independent caller.

The proposed global coordinator is a small Pi loop in the existing Mac companion, with the chosen voice frontend delegating tasks. **Whether Pi performs computer use or confines itself to workspace/window management and contextual prompt/input routing remains open.** Coding-agent-owned control and shared access are alternatives to evaluate before implementation. Whichever agent acts, existing services retain workspace/process ownership, shared providers own capture/control, and Vision's existing `WindowGateway` retains presentation ownership. The model discovers how to launch and navigate an app; application code supplies stable targets and observable effects.

The user's current preference is **Codex's installed CUA runtime** rather than starting with an open-source driver. Independent native reuse is demonstrated. The specialized browser provider has a distinct unresolved Codex session/access dependency, but **Chrome also works through native Mac CUA**: a November 9 live test operated page fields, buttons and an iframe without invoking the browser provider. Do not make specialized browser provisioning a prerequisite for the first web demo. Revisit interfaces, operational independence and release terms with the user before making a shipping commitment. Keep the open-source comparison available without implementing multiple providers up front.

The November 9 browser experiments provide working model-free alternatives: Playwright MCP accepted companion-owned browser contexts, Playwriter retained JavaScript page handles over direct CDP, and agent-browser rejected closed pinned targets. These headless local trials do not establish extension takeover, native capture identity or Vision streaming. Browser provider choice can be evaluated separately from native Mac control while retaining the same ownership and presentation boundaries.

The user now explicitly wants a large spatial workspace without a matching Mac desktop. Treat native capture as one source adapter. Browser-owned rendering can preserve the shared target and Vision gateway while avoiding visible Mac browser windows. Owning a Chromium host is a candidate to compare, not a decision to fork Chromium or ship several browser backends.

Before integrating a production agent, resolve the initial control responsibility through the [focused ownership comparison](2026-11-09-agent-control-ownership.md#decision-before-implementation). The proposed integration remains one model-driven simulator request through the real execution and presentation path, using the chosen controller. The exact tool grants, voice API choice and larger workflow prompt set remain design work. Broad feasibility retesting is not needed to answer this interaction question.

## Remaining decisions and validation sequence

Consolidated November 9, 2026. This is a synthesis of the linked evidence, not a new experiment or approval of additional sample prompts. Most remaining work is a small integration or a product decision. Another broad provider survey would add less value than exercising the actual agent-to-Mac-to-Vision path.

### Decide the product experience before expanding it

| Open item | Decision or evidence still needed |
| --- | --- |
| **Browser hosting and spatial scale** | Choose whether ordinary Chrome windows suffice initially or whether managed/offscreen rendering is needed. “Own Chromium” is not yet selected. Compare retained pages with active renderers, laptop interference, account isolation and CPU/GPU/encoder/headset cost; use the same controlled page for the displayed frames. Agree on a useful active-window budget rather than promise unlimited rendering. Test the [proposed scaling workload](2026-11-09-spatial-surfaces-without-desktop-windows.md) before accepting an embedder's maintenance cost. |
| **Voice, wrist context and spatial placement** | Choose one voice/delegation path after the typed workflow works; Poncho2's inspected GPT-Live/Pi coupling is not literal GPT Realtime. Validate originating-window context before menu focus changes, “this/other workspace,” slash commands versus dictation, corrections and interruption. Determine supported placement/grouping on physical Vision and whether initial human takeover requires direct headset pointer/keyboard input. We have not established arbitrary repositioning of existing windows or passive eye-gaze targeting. |
| **Real workspace preparation** | Exercise the user's Poncho2 examples with actual worktrees, terminal agents, separate frontend environments and the intended simulator. Let the agent discover setup and navigation; verify partial failure/retry without duplicate processes. Useful automatic workspace naming is already a requirement, not another preference to decide. Names belong in existing metadata, and explicit user renames must be respected. |
| **Away-from-Mac behavior** | Decide whether the initial promise requires launching a cold simulator while locked or supports an already prepared simulator on an awake Mac. The latter has live evidence; cold boot/install, whole-system sleep, lid closure and logout do not. Test the chosen promise and expose lock, provider health and recovery state accurately. Native desktop gating is our policy; the experiment did not prove raw ScreenCaptureKit must fail under lock. |

The larger prompt catalog remains awaiting review. Select a few that discriminate between architectures: workspace preparation, code verification, immediate navigation while Codex is busy, two concurrent workspaces, and Stop/human takeover. Do not implement the whole catalog to discover the first interaction model.

### Qualify the selected path before wider rollout

Keep hardware H.264 as the initial video path. A focused physical-headset comparison should measure real text readability, input-to-visible-result latency, delivered cadence and bandwidth under several live streams. Compare ordinary real-time HEVC and actual WDA JPEG-to-H.264 only where they can improve that experience. The [26 Mac codec cases](2026-11-08-mac-codec-benchmarks.md) establish short local encode/decode behavior, not headset capacity, power or long-session reliability.

Then qualify the production app/helper identity: fresh permissions and repair UX, runtime startup with Codex closed, update compatibility, target closure/relaunch, minimized/native-dialog behavior, connection loss, backpressure and a longer session. Permission attribution in the disposable probe is not production onboarding coverage. Preserve the known standalone XCTest failures and the draft PR's unresolved WebKit viewport timeout until their causes are addressed; no all-green reliability claim follows from this research summary.

**Recommended order:** select the small acceptance-prompt set and initial agent responsibility; qualify the preferred runtime connection and parallel browser path; connect one typed simulator workflow through the real gateway; add real workspace preparation and the chosen voice/wrist entry point; use one focused Vision session for context, presentation, media and the agreed lock-state promise; harden that supported configuration before broadening it. Provider and gateway work can overlap where independent. Each step should close a named uncertainty, not add another framework.

No broad window-management rearchitecture, durable coordinator, Chromium fork, multi-provider framework or codec-switching system is justified by the current evidence. Existing Mac service ownership and Vision's gateway already supply the necessary boundaries. Internet transport, physical iPhone support and whole-system sleep need separate requirements before they become first-release blockers.

## Evidence boundaries

Native multi-window streaming and independent simulator streaming/input were exercised on a physical Vision Pro. The user confirmed the final locked simulator counter changes and native-view recovery after unlock. These results do not establish full-system sleep support, cold simulator boot while locked, production Pi/MCP integration, automatic exact-window association or direct headset pointer/keyboard interaction. Standalone XCTest failures remain recorded.

The probe is isolated from production sources and build dependencies. Local builds, device recordings/screenshots, live-session logs, connection files, certificates and keys remain ignored. The repository contains written findings, reproduction sources, and the synthetic benchmark's credential-free measurement JSON, CSV and journal. Source references in the notes are pinned to the inspected revisions, including older baselines; use the current application architecture when implementing the proposal.
